# RESULTS — development results log

**Append-only.** This is the human-readable development results log for the
mini-inference-engine. Newest entries go at the bottom; nothing here is ever
edited or deleted once written — if a number was wrong, add a new entry that
corrects it and say so.

Each entry records:

- **Date** — when it was run.
- **Stage** — which part of the build it exercised.
- **What was run** — the exact workload / harness / device.
- **Raw numbers** — the measurements, not just conclusions.
- **Interpretation** — what the numbers mean and, crucially, whether the
  metric is *valid in that regime* (a recurring theme: throughput/latency
  metrics collapse to nonsense when a single batch delivers simultaneously).

Two producers write here:

- **`benchmark.py`** appends a timestamped section automatically after every
  run (raw JSON also lands in `results/raw/`).
- **Manual entries** are welcome for non-benchmark milestones (verification
  runs, seam checks, one-off floods). See `results/README.md`.

### Jul 9 — Stage 1b verification (FakeRunner, CPU) · *reconstructed from dev logs*

**What was run:** 6 concurrent requests driven through the sequential fallback
worker (FakeRunner, CPU) — no real model, plumbing check on the queue/worker
path.

**Raw numbers:**

- Per-request latencies: `100.3 / 149.9 / 199.1 / 248.1 / 297.7 / 344.4` ms
  — a clean **~50 ms staircase**.
- `/metrics`: `p50 = 248.1`, `p95 = p99 = 344.4` ms, `tokens_per_sec = 286.8`.

**Interpretation:**

- The 50 ms staircase is the signature of **sequential service under one batch
  window** — requests are serviced one after another, each ~50 ms behind the
  last, not concurrently.
- `p95 = p99 = 344.4` is a **percentile collapse-to-max** artifact: with N = 6
  samples the 95th/99th percentile both resolve to the single largest value.
  Not a real tail — just too few samples.
- `tokens_per_sec = 286.8` is **valid here**: because the staircase spread the
  completions across a real time span, the completion-to-completion span the
  throughput metric divides by is meaningful.

### Jul 10 — Stage 4 seam verification (real ModelRunner) · *reconstructed from dev logs*

**What was run:** seam verification against the **real `ModelRunner`**, two
environments.

**Raw numbers & interpretation:**

- **CPU flood** — 6 × 16-token *identical* prompts: all finished at **~23.9 s**,
  essentially flat (**~10 ms spread**). Batching amortization is visible
  (all six share the batched forward passes), but this is a **CPU functional
  check only**, not a performance number.
- **T4 varied-caps flood** — caps `8 / 12 / 16 / 20 / 24 / 32`: every request
  received **exactly its own cap** — the positional invariant was empirically
  confirmed (prefix-extension texts came out as **lockstep greedy**). All
  latencies clustered at **~3028 ms** (spread **~1.8 ms**). That flat cluster
  is the **keep-and-ignore fairness cost**: finished sequences are kept in the
  batch and ignored, so everyone pays for the slowest cap.
  → **T4 RECOMPUTE BASELINE ≈ 3028 ms** for a batch-6 run at a 32-step ceiling.
- **`/metrics` artifact:** `tokens_per_sec = 2,549,510`. This is the
  **metric-validity regime lesson**: when a single batch delivers all
  completions simultaneously, the completion-to-completion span collapses to
  microseconds and throughput blows up to a meaningless number. The metric is
  **only valid under sustained traffic**, where completions are actually spread
  out in time.

## Stage 3 — KV Cache Port (Jul 22)

**Device:** Tesla T4 · **Model:** Qwen2.5-1.5B (fp16) · **Tokens generated:** 256

| batch | recompute (tok/s) | cached (tok/s) | speedup |
|-------|-------------------|----------------|---------|
| 1     | 22.5              | 27.58          | 1.23x   |
| 2     | 49.3              | 58.05          | 1.18x   |
| 4     | 97.9              | 114.15         | 1.17x   |
| 8     | 148.5             | **230.66**     | **1.55x** |

> Recompute figures are from the Jul 9–10 run — same device, same harness, different session.

**Scaling per doubling**

| doubling | recompute | cached |
|----------|-----------|--------|
| 1 → 2    | 2.19x     | 2.11x  |
| 2 → 4    | 1.99x     | 1.97x  |
| 4 → 8    | 1.52x     | 2.02x  |

### Why the gain grows with batch size

The KV-cache optimization produced a larger gain at batch 8 than at smaller batches because its payoff depends on how well the GPU is utilized. At batch 1, execution is heavily affected by model-weight movement, small kernel launches, and other fixed overheads, so removing computation does not translate directly into an equal reduction in runtime. At larger batches, the GPU has more parallel work and recomputation becomes a more meaningful bottleneck. The cache eliminates the need to send every previous token through all Transformer layers again — including the QKV projections, attention operations, output projections, and MLP blocks — because only the newest token traverses the model while the previous key/value states are reused.

### The scaling bend straightened

The optimization also improved the system's scaling behavior. With recomputation, throughput gains weakened as the batch doubled: 2.19x from batch 1 to 2, 1.99x from 2 to 4, and only 1.52x from 4 to 8. With KV caching, the corresponding gains were 2.11x, 1.97x, and 2.02x, meaning the 4-to-8 scaling bend was effectively straightened. The cache therefore did more than improve batch-8 throughput — it removed enough repeated work to restore nearly linear scaling at the largest tested batch size.

### Prediction vs. measurement

I predicted approximately 300 tok/s at batch 8 but measured 230.66 tok/s. The mechanism was correct, but my prediction incorrectly treated the cache speedup as nearly constant. In reality, the gain depends on both batch size and sequence length. This benchmark generated 256 tokens, so it measures only one point in the batch-size × context-length space. At longer contexts, recomputation would become increasingly expensive because every previous token must repeatedly traverse the full model, while cached decoding would still process only one new token per step. A useful follow-up experiment would therefore hold batch size fixed and sweep context length to measure how the cache advantage grows.

### Consistency check

Cached `generate_batch(batch=1)` reached 27.58 tok/s, while the separate sequential cached path reached 26.66 tok/s — a difference of less than 4%. Their close performance confirms that batch-1 now represents the batched implementation processing one cached sequence, and provides an internal check that the KV-cache port was applied correctly.

**Regression:** `verify_decode` 4/4 exact — greedy output unchanged by the port.
